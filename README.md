# From Prompt to Vulnerability

**Evaluating security risks in AI-generated proxy tunnel code across multiple large language models**

A comparative security study of code written by ChatGPT (GPT-4) and Claude (3.5 Sonnet). Both models are asked to build a proxy tunnel in Python and in Java. The code is then tested with static analysis and penetration testing, and the full prompting history is analysed to see how vulnerabilities appear and change from one prompt to the next.

> **Status: research design complete. Experimental results are not yet published in this repository.**
> The full proposal is in [`docs/research-proposal.pdf`](docs/research-proposal.pdf). Everything under "Planned method" describes the study design, not finished results. Nothing here reports a finding.

## Why this study

LLMs now write production code, and earlier research shows that a large share of what they produce is insecure. The literature leaves three gaps, which this study targets:

1. No existing work compares ChatGPT and Claude directly on a **network-facing implementation task**.
2. Few studies combine **static analysis and penetration testing** on the same code, so exploitability often goes unconfirmed.
3. No study treats the **full prompting log** as research data, even though earlier work suggests repeated fix-it prompts can make code less secure.

A proxy tunnel was chosen because it exercises input validation, connection management, data forwarding and socket handling together.

## Research questions

1. What vulnerabilities appear in proxy tunnel code generated by ChatGPT compared with Claude, in Java and in Python?
2. Which vulnerabilities are found by penetration testing and which by static analysis, and how do the two methods compare?
3. How does the iterative back-and-forth between user and model affect the vulnerabilities in the final output?

## Planned method

| Stage | What happens |
|---|---|
| 1. Prompting | One identical starting prompt describes the proxy tunnel. Four sessions follow: ChatGPT Java, ChatGPT Python, Claude Java, Claude Python. Each continues until the code works. Every prompt, response and error is logged in full. |
| 2. Static analysis (SAST) | Bandit on Python. SpotBugs with the FindSecBugs plugin on Java. Findings classified by CWE and severity. |
| 3. Penetration testing (DAST) | Each implementation runs in an isolated VM. Nmap maps the attack surface, OWASP ZAP scans it, and manual testing checks whether static findings are exploitable. Findings scored with CVSS. |
| 4. Analysis | Compare models and languages. Split findings into static-only, pen-test-only and confirmed-by-both, and report the confirmation rate. Trace vulnerabilities across the prompting log. Triangulate all three data sources. |

**Environment:** Ubuntu 22.04 LTS virtual machine, isolated with no internet access, JDK 17 and Python 3.11.

## Ethics and safety

All testing stays inside an isolated VM. Findings will be reported at a defensive level of detail, with no exploit code and no step-by-step attack instructions. If a new vulnerability pattern emerges, the vendors (OpenAI and Anthropic) are to be informed before public release.
